# 通用施组编制（r21-泾县医院）

有效版本 2026-11-20-r21。使用状态schema 3.2、source_coverage/source_response_review v1、technical_review v1及格式硬审1.17.0。阶段checkpoint核对同稿评分报告。

## 1. 一条生产主线

先盘点与质询 → 内容规划及准入 → 逐模块写作和复核 → 40%/75%全局校准 → 冻结整稿 → 内容、Word及页数验收 → 交付。默认一次，用户交付最多三批；内部模块、保存、试排和返修不限次数。

**先运行“next”取得当前动作，完成后再取下一步。** 它只输出当前步骤和缺项，避免读取整个大状态文件。退出2表示任务仍有工作，按next_action继续；退出3才是执行异常。不能将Word已排满、草稿已保存、某一个检查PASS或外层进程0当作任务完成。

```bash
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json next
```

首次任务按返回动作执行init，填写真实资料、规划后preflight。init创建BLOCKED骨架并返回2属预期。**获得PRE_DRAFT_ALLOWED才批量编制；长文先获PILOT_DRAFT_ALLOWED，仅制作代表性样章。** 每模块完成立即复核并module-checkpoint；到节点先checkpoint再推进。命令和字段按第2节定位，不自行创造状态名。

缺资料或冲突时集中询问、独立登记，继续有依据的部分，受影响内容尽量转成条件化措施、实施前核验和不同条件下的处置。不擅定未知事实、不把沉默当无更新。用户已授权“暂按现有资料”时，按04登记authorized_current_sources、答复来源、safe_scope及pending_confirmation；它允许相应编制，不等于确认官方无更新，不免除现有资料能够完成的核查。

遇FAIL/ERROR先定位、保存恢复点并修复依赖问题；独立可做的资料核对和内容准备继续。不得为了消除报错批量填true、删需求、放宽页数、改成局部模式或重置历史。现场不另写“汇总成功就返回0”的交付程序，统一调用包内delivery；必须读取其任务状态和失败项，不能改称编制稿就结束仍可完成的工作。

### 四项硬审的执行时点

| 时点 | 必做动作 |
| --- | --- |
| 编前 | 在原计划登记有效清单表、指定图种与必验要素、适用措施与完成条件、关键工序与工效窗口。按01从原行取值，按03／07核空间资料；缺资料在原状态登记，独立模块继续。 |
| 模块完成 | 从当次正文核工序、触发、做法、标准、异常处置。逐项填写实际位置、引文和充分性判断；计算关键持续时间，核同窗资源占用，已插图件查看本稿。缺项退回责任模块。 |
| 40%／75% | 对已纳入的模块和实际合并稿运行checkpoint，逐项核清单、图页、措施及数据一致性，跨模块复算依赖、技术间歇、资源与到货。保留原节点、快照和复核证据。 |
| 最终交付 | 从冻结Word反查正文、表行和图注；核每张指定图的Word总页和图上位置；以最终原文复核措施，重算计划并对照图文。四项全过并满足原有交付条件才正式发出。交付端执行04的release_docx，失败结果随本次稿件保存。 |

已有r20状态就地增补 `plan.hard_checks`、模块证据和同稿内容核验，沿用原模块ID、资料和历史记录。历史节点缺证据时按当前补救复核登记实际时间；有保存的原阶段稿时可核该稿，禁止重建或回填历史测量。

以施工单位资深工程师或项目总工的专业视角编写可实施正文。专业判断以当前资料、领域库和已核验的适用规范为据。按用户要求、AGENTS和有效招标确定项目规则，字号按第3节确定，其余执行招标硬性要求。案例、例图只借鉴写法和视觉，项目事实回查原件。

先验证当前会话能调用的Word通道：Windows本机COM或已有GitHub Windows Runner。电脑安装Word不代表会话可调用。依赖只按需要预检一次，不反复安装。读取异常先处理原件/转换件，PDF枚举可自动采用备用读取器，仍须回看原图。Word离线允许按既有规则登记PROVISIONAL，最终必须Word实测；长文样章不得用估值替代。

## 3. 启动与内容规划

拟纲前读[07 项目重点、标题与字号](references/07_项目重点标题与字号.md)。在已有规划中填写project_response，供编前、阶段和同稿交付共用。二、三级标题分别覆盖至少15、20个不同的重要原文词或准确变体，属于硬要求。按提示词增设某层级标题时同步提高该层关键词目标。先按评分及项目特征选定前三项，再按正文版面分别落实至少20%、13%、10%。编前提示词明确指定正文字号时，用Word实测估算容量并分配到施工内容。招标指定的图表须锁定章节目名、题注和实际内容。

1. 盘点全部有效资料、附件目录及版本。原文逐单元读取、处置，评分子条件反查并核施工范围；清单、费用、检测、小分项及接口同样提取。扫描仅建立范围，不代表已经阅读；不能只搜关键词或用知识库摘要冒充原件。
2. 集中询问最新澄清、答疑、补遗、补充材料及系统新要求，提出影响范围、路线、评分和确定承诺的问题。已明确答复的引用真实来源，不重复问；先穷尽可访问资料，不将检索转交用户。
3. 第一项页数动作读取当前唯一项目页数脚本。换项目只替换此脚本；目标、容差及前置扣除以它为唯一来源，不在通用Skill、工作流或另一个长期参数表重复维护。实际完整封面目录占页不一致时据依据修正项目脚本并重测。没有脚本只跳过页数规划和测量，内容/图文/交付仍执行。
4. AI在篇幅规划前确定项目格式。**各部位字号先用编制前提示词明确指定的值，未指定的部位参照有效招标及补遗。** 按04生成同一份格式规则供Word样式和审核使用。招标未明确时封面及一级目录共第1页，正文第2页、显示页码1；全篇三级标题，默认章/节/一，每章有节、每节有实质三级标题，不机械3×3。**正文一级和二级标题居中，三级左对齐，静态与Word硬审均须通过。** 招标另有明确规定时按04登记依据。自拟二级标题简短，保留一个主要评价判断或控制点，禁止逗号/分号串句；招标锁定标题保留原文。拟纲时按表名或表内标题识别清单中全部「分部分项工程量清单计价表」，优先从其项目名称及特征提取施工关键词，自然写入相关二、三级标题，做法见02。
5. 先建立“来源重点/评分子条件/实施义务→需求→主响应模块→具体论述完成条件”，每项需求恰好一个主响应位置。先判断内容容量，再分配正文、表格、图件及接口预算，不平均按章分配、不重复计页、不用空白和重复材料填充。
6. init、source_coverage扫描及评分原文冻结后，完成真实处置和规划，再preflight。目标达到200页的长文按05完成至少两个代表模块的真实Word样章，校准文字密度和预算，再draft-ready。旧状态据实增量迁移，不能补造启动和历史节点。

## 4. 模块与阶段校准

用template生成原有复核JSON的空结构，AI填实际结论和证据；模板默认pending/false，绝不自动通过。模块正文源须为真实MD/TXT/DOCX；生成器代码、标题或探针缩略稿不能冒充正文。

提示词明确要求密集标题或短段时，按07落实数量、段长和逐项关键词；允许一个三级标题只有一两句完整的施工措施，一个模块可以包含多个三级标题。每个模块写足“对象—工序—操作—资源—控制—检查—偏差处置”，不机械套字段。立即核对事实来源、技术深度、接口、重复和施工语言；评分责任按原文及优秀条件逐项检查，全部主响应需求按完成条件检查充分性；五项专业复核并入同一记录，不另开台账。引文必须在当前模块正文中，未完成项先补强。

```bash
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json template --kind module --id M01 --source 项目/正文/M01.md --output 项目/复核/M01.json
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json module-checkpoint --id M01 --source 项目/正文/M01.md --review 项目/复核/M01.json
```

40%/75%按施工内容和评分责任选择连续模块前缀，保存实际合并阶段稿；**测量报告MEASURED只是输入，不代表阶段校核通过。** 同步生成绑定该稿的阶段评分报告，checkpoint同时核对模块、篇幅、当前评分依据及同稿评分报告。75%之前先完成40%；已实测前缀＋剩余模块预算＋机动量须在最终范围内。

```bash
python scripts/评分响应核验.py 项目/项目评分清单.json --phase 40 --document 项目/stage-40.docx --report 项目/score-40.json
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json checkpoint --stage 40 --document 项目/stage-40.docx --report 项目/word-40.json --score-report 项目/score-40.json
```

75%同法。阶段复用未变模块证据，检查跨章接口、总体覆盖、剩余责任及篇幅；不重复整篇审核。变化使报告STALE时，只返修受影响正文/预算并复测，不扩大容差。恢复读取最后有效正文源、模块登记、来源、参数及阶段状态，禁止重新编制已完成整本。

## 5. 贯穿全篇的质量要求

- 依项目条件作出施工决策，按评分子条件组织履约证据。原件中的施工对象、特别限制和交付接口应实际影响方法、资源、进度、质量安全与验收。每章用精练专业的施工语言说明本章承担的判断和证据；模块复核及40%/75%抽查跨章是否自洽，定稿将重要承诺反查原件与技术计算。
- 对关键工法核清作用机理与适用边界，根据本项目工况写清选用理由、关键控制条件和核验方法。
- 对已用关键参数跨来源检索全部相关出现，区分部位、版本及数值性质。回查规范编号、名称、版本和控制参数。**在重要措施、参数、验收判据或承诺所在正文段落列依据全名和可回查位置。** 约50页正文至少15条有效引用，数量按中等约束，长文及计数口径见04。计算保留公式和输入，策划写明条件和可行性依据。
- 按用户固定口径规避争议，图纸瑕疵或与清单冲突以有效清单为主；方法、资源、质量安全和验收措施仍写充分。独立记录保留双方原文、采用依据及关联复验；handled表示编制处置完成，不冒充官方统一。
- 正式正文不得混入待办、审查意见、自评或内部状态。按语义区分正常施工表达与内部编制语言，定点返修；独立冲突和审查记录与正文分开。
- 先落实招标逐字指定的图表。默认三类彩色技术图的题名为施工功能分区示意图、施工进度横道图、施工进度网络图；招标点名对应功能图时采用指定原名并落实全部功能，覆盖关系登记到visual_policy。另从全项目选择并生成1—3张有技术价值的功能彩图。精确数据、拓扑及进度用可复核代码/矢量生成，与正文和资源工期同源。
- **正文有效图与数据表合计至少15个，按中等约束执行。** 规划时落实位置和篇幅，定稿按实际对象计数。低于15个时先补有价值的图表，确有项目限制时在现有WARN记录留实际数量、差额及依据，见06第二节。
- AI判断照片价值：需要照片则用可确认的真实素材，缺素材留明确主题的有框占位；不适合照片则实际生成针对性替代示意图。有效特殊要求引用原文登记visual_policy。不能清空图单逃检、虚构实拍或以三张必备图冒充照片主题替代图。
- 未有相反招标要求时A4竖版、全篇自然流排，不强制换页、不用普通正文锁段转移空白。图表各自全篇连续编号；目录是真实自动目录、点引导符和页码右对齐。表格按内容分列宽、清除意外缩进，短内容居中、长说明左对齐，实际查看换行、跨页与可读性。细则均在03/04，不另造一套标准。

## 6. 冻结、验收与交付

更新目录、题注和引用，保存并重排后冻结当前DOCX及format_rules。按04生成并填写内容溯源核验：十项回查、参数/冲突、逐节标题支撑、原件独立反查、全部需求充分性、语言与实际图文视觉检查；复用仍有效的模块记录，仅增量审变化项。核对关键词实际命中、前三项实排占比、招标指定图表技术内容及已触发的字号预算；汇总数字密度与图表数量的结论。

对同一冻结文件完成content-review、final-ready、评分最终核验、静态硬审、Microsoft Word格式与项目页数硬审。按03第一节单独交付完整的《施工组织设计技术评分模拟自评报告》。末页留白严格低于20%，实测末页及其前最多4页并处理异常。篇幅差在对应实质章节处理，禁止改版式或搬空白凑页。新文件、新来源或规则变化后，更新受影响的验收证据。

最终统一调用delivery（完整参数见04）。它保存流程交付结果.json并传播失败退出码：只有task_complete=true且formal_release=true可声明全流程完成；通过但含照片占位只允许约定的草稿交付，不能声称最终放行。失败可保存成果和如实汇报，但继续完成可修复事项，不自行结束委托。不能用另写汇总程序、批量改状态、借局部复审或伪造历史节点取得合格标记。

真正局部返修在原内容核验记录的local_review_scope中保留用户授权原话、来源、范围及原稿快照；只标记局部验收，不替代全文流程。旧稿缺历史记录时保留缺失事实，按授权做当前补救核查，不将事后检查冒作当时已通过。

**能力边界：**脚本检验结构、版本、证据对应及调用条件；AI负责原件阅读与专业判断。next是推进提示，不能自行接管桌面所有写文件或发送动作。部署时须实际验证桌面/Runner对失败码和交付结果的处理；未接入执行端控制，不得声称绝对不可绕过或绝对零遗漏。
