# 施工技术标实质响应

编前把本页项目规则填在既有状态的 `plan.bid_requirements`。旧状态从 `bid_requirements.template()` 补入，保留资料、模块编号、历史快照和既有复核。变更后重新准入，补核实际留存阶段稿；不得伪造历史测量。以实际项目资源、计划和最新版招标原件为准。每个硬失败回到对应模块修正。脚本核可复算和可定位的证据，编制者逐项判断专业适用性。

## 编前与计分

填写 jurisdiction（工程所在省市县）、as_of（适用基准日期 YYYY-MM-DD）。本页 source、validity、adoption、person_proof、score_sources 均引用已入库原件，使用 `{source_id,unit_id,quote}`。来源包含行业主管部门或官方现行文本、发布/废止公告、属地文件等实际使用的版本；原件为扫描件时保留原件对应关系，经核验的可读转换件按01登记。查最新补疑。参考模型和高分案例只用于发现问题。

- score_sources 以真实赋分项ID为键，引用能核对满分的招标原文。score_effects 按每个 scoring 需求ID登记 kind、scope、source。kind 选“独立项零分、综合项评审、明确扣分、否决、未明示”。scope 写清该后果适用哪一级、什么情形。综合项只按招标给定层级模拟评分；缺分项赋分不拆造小分。五维用于检查。30/25/20/15/10、42%或108项只有招标原文明示时才可作对应项目规则。禁止从查重率、引文数量或图表数量推算项目分值。
- decisions 每项填 id、requirement、module、source、condition、choice、verification。抓真正改变工法、配置、窗口或验收的项目条件，如在用通道只能分段切换。对工程地点、地质、工期和点名重难点按原件判断适用性，并追到相关章节。工况不足时给出核实的责任、时点和分情形做法。
- screening 逐项筛国家强制要求、属地监管要求、工艺、安全、岗位资格、危大工程、临电、扬尘；各填 applicable、reason、source。按专业补充其他风险，每个触发项进入 obligations；属地筛查覆盖本项目适用层级，不将外地措施冒作当地强条。无基坑工况给出排除依据。义务即使没有独立分值也必须响应。
- obligations 各填 id、requirement、module、topics、authority（依据全名）、version、clause、level（国家/行业/省/市/县/项目）、territory、scope、operation、role、check、acceptance、source。validity 除原件引文外填 status=有效、effective_from、适用时 effective_until。核对标准性质、条文强制性和实际版本日期；招标依法引用外地技术措施时填 adoption，按合同适用要求表述。岗位资格填 qualification、verification_time，声明已获证时填 person_confirmed=true 和 person_proof；匿名正文只列允许的岗位能力。
- 以上引文与工序相关字段按正文实际写法填写。模块 review.bid_evidence 以义务/施工决定 ID 为键，各字段映射实际 L行号；阶段、终稿以 P块号或 T表号R行号重新定位。每项必须能在实际检查对象中找到。已核条件须有专业判断、实际责任和闭环处置，沿用既有 measures、response_review。重要数值及单位保留在对应正文或附表，按06记录数字密度适配结果。

## 资源与附表

沿用 hard_checks.schedule.tasks。每个关键活动填 productivity_basis（正文实际工效推导，含工程量、有效窗口、班组/机具能力与依据）。task.capacity 填 source（原件试验、定额或设备性能资料）、calculation（推导过程）、crews、plant。crews 的班组编号对应 {trades:核定班组构成,rate:该组每小时有效工程量}；plant 的设备编号对应 {operation:作业环节,unit:工程量单位,unit_rate:单台每小时有效产量,conversion:额定参数折减或换算依据}，辅助机具用 {support:具体用途}。各串行环节分别校核瓶颈，同环节并行能力可相加。按既有规则复算。bid_requirements.crews 以稳定班组编号为键，填 trades（工种到每班人数的映射）、shift、entry（到场阶段或时点）、basis。equipment 以独立调配的设备组编号为键，填 count、spec、capacity、entry、basis。招标点名型号就核型号，其他情况核拟用规格与有效能力，并注明自主策划依据。共享组按整组占用，可分别调用的机组分配不同编号。review.bid_evidence.resources 以活动ID为键，productivity 填正文位置，每个班组/机组编号下 locations 填含名称、人数或台数、规格能力、到场及班次的实际段落/表行位置。每个工种与人数、规格与台数应就近对应，例如“安装工2人”“D-8共2台”。

逐份查招标目录、正文、附件表式和补疑。从实际 Word 原名、同名章节、题注定位到唯一表对象。annexes 以每张指定表原名为键，填 module、source、basis、headers（逐行物理单元格文本，含多行表头）、key_col（列号从1起，组合键用 key_cols）、required_cols、rows。对象从清单、专业范围、阶段/资源或招标样式独立列齐。覆盖项没有技术依据时保留缺口。不同表用各自字段，不设全项目统一最低行数。

例如劳动计划表的列为“工种、拆除阶段、安装阶段”。每个 rows 项用 key 标识工种，用 cells 的字符串列号指明取值。取值方式：

- 独立内容填 `{"value":"实际取值","basis":"招标页条、清单原行或自主策划的计算依据"}`；不适用格填 `{"na":"不适用","reason":"具体工况"}` 并在表中原样显示。数值为零用零，保留数值和计量单位的实际含义。
- 资源表填 resource_kind=trade 或 plant，task_ids 为所覆盖的关键活动ID；局部覆盖需 scope_basis。resource_cols 列出与资源目录相关的必填列。主体数量从同一套资源和活动数据读取。标准设备表的 equipment_fields 将实际列号映射为 count、spec、capacity 等字段，例如数量用 `{"resource":["equipment","钻机A","count"]}`；行名与编号不同用 resource_key 对应。人员配置字段也可用 `{"resource":["crews","安装班","trades","安装工"]}`。
- 分阶段数量另填 phases，用表内阶段名映射 [首日,末日]，表头简写时用 phase_labels 登记。填 `{"phase":"安装阶段","peak":["trade","安装工",8,12]}` 或 plant 同式，按同窗实际投入求峰值。项目有非关键收尾日时 project_days 用核实的总工期。行列互换时按实维护。核清峰值、工日、班次的口径；招标要求工日或台班时用 workdays 代替 peak，并在四项后加第五项“每工日/台班小时数”，按实际占用窗口累计人时或机时后换算。
- 例：D1甲班2名安装工、乙班3名安装工同时施工，则该时段需5人；两个班组同日首尾相接时，峰值取3人。原计划追加但未用到的备用窗口不重复占用。
- 缺表、空表、关键格空白、漏对象、误用型号代替台数、数值与班次或进度不一致，均退回。核验输出带表名及实际行列。15个图表的既有数量规则单独执行。

## 正式格式及实际提交件

format.source 登记招标格式依据。逐项判断硬性、建议及未明示。fonts 按部位填强制字号；color 仅填明示配色（color/monochrome/custom）；pages 填 null 或 {scope:body或total,max:上限}；anonymous 填布尔，deliverable 填 docx 或 pdf。sources 下对生效的各项留原文单位。硬性规定优先，提示词在允许的范围内生效；项目唯一页数脚本必须与招标上限和封面目录口径一致。模板默认不得覆盖明示条款。

- 把 format.fonts 复制为 format_rules.tender_font_sizes，deliverable 写入 format_rules.submission_format。字号预算以最终有效字号实排。横道图、网络图统一调用 `schedule.chart(model,kind,color_policy)`，第三参传 startup.visual_policy.color_figures；将返回的实际 SVG 和同源 PNG 嵌入 Word。黑白图用灰阶和星号区分关键活动。进度和依赖变化仍须重绘。
- 暗标时在 identifiers 录入全称、简称及其他禁止标识。自动扫描正文、页眉页脚、文本框、修订批注、属性和图形说明。人工打开同稿看图内Logo、图签、水印、签名、封面及公司页脚。复用 `submission_identity.surfaces(path)` 输出的位置与图像/版面哈希；review.identity.docx（及实际交PDF时的 pdf）填 sha256、visual，后者逐位置登记 sha256、clean=true、finding（实际所见）。允许实名的指定区只按招标在 format.permitted 登记具体位置和名称，并在 permit_sources 为每个例外绑定条文。不得把全篇或全图列为例外。
- 交付PDF时用正式 Word 审核的 submission_format=pdf 导出。本次报告 pdf.sha256 对应实际导出字节。将该PDF作为 review.submission_pdf，填 path、sha256、document_sha256。美化使Word或PDF变化时重新核对应提交件，按实际后缀调用 release_docx.py。暗标PDF须逐页检查，图片扫描页也须核。最终文件名不得暴露身份。
- 正式交付运行既有 delivery 与 release_docx；失败返回非零、formal_release=false。原稿仍可保留为工作稿。测试用例在 tests/，先跑全量单元测试，再用实际 Word 的冻结输入运行项目验收。
