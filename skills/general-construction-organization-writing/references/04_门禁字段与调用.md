# 门禁字段与调用

目录：启动与篇幅；原资料覆盖与充分响应；项目脚本替换与唯一来源；Word通道；静态核验（格式与目录、数据表排版、语言、图件与照片）；内容溯源；自然排版与末页留白；交付汇总；环境依赖。按SKILL.md的阶段表定位小节，启动只读启动字段、原资料覆盖的启动部分、唯一页数来源和所用Word通道，不预读最终静态/溯源/交付细节。

## 启动与篇幅

首次运行（命令均以技能根目录为基准；运行期文件放项目工作目录）：

```bash
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json init
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json next
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json preflight
```

init创建BLOCKED骨架并返回2是正常结果，不是通过。不强行重置已有状态；从真实记录补足必填项。

每次保存/恢复后用next取得当前动作，不读取整份大状态替代推进。next退出2表示尚有步骤；异常退出3。最终直接调用delivery，禁止另写忽略子检查退出码的父汇总；失败继续返修，保存草稿不等于任务完成。

`startup`由AI维护，须填：
- `sources`：对象数组，每项`path`（相对状态文件目录或绝对路径）、`sha256`、`role`；招标原文role=`tender`，图纸=`drawing`，清单=`boq`，补遗=`amendment`，知识库=`kb`。
- `latest_updates`填写`status=confirmed_none|provided|authorized_current_sources`、`asked_at`、`reply_text`、`reply_source`，引用用户实际答复。provided还填`provided_paths`并将全部文件纳入sources。用户明确允许按现有资料继续时用authorized_current_sources，再用safe_scope和pending_confirmation记录可编制范围和仍待确认事项。按授权范围编制、保存稿件并完成可做的核查。全文delivery前据实确认最新资料，更新授权记录并重新preflight。
- `critical_questions`：每项`question`、`status=resolved|bounded`、`evidence`；bounded还须有`safe_scope`。图纸瑕疵/与清单冲突已按用户口径规避或采用清单时，bounded记录有效清单及采用口径，继续相应正文；原始资料未统一不等于编制未处理，不能冒充官方确认。其他未知事实仍不得擅定。
- `questions_review`：资料缺失/冲突判断结论；即使没有问题也说明已检查哪些范围。
- `batch_plan`：`count`为1—3整数、`reason`、`batches`数组（各批范围）；内部快照不计批次。
- `word_channel=local_word|github_runner|unavailable`，`word_capability_evidence`写实际调用证据/明确阻塞点。
- `visual_policy`：`version=1`；`real_photos`含`decision=required|schematic|omit`、`reason`及`replacement_figures`图名数组，分别表示选照片、直接生成替代示意图、有明确特殊要求允许省略；`color_figures.mode`默认color；`additional_figures`含三图之外的1—3个`names`及整体价值`reason`。特殊要求使用对应子对象的`override={source_type:prompt|agents|tender,source_ref,quote}`保留原文及位置；招标冲突仍按既有流程处理。启动只策划图名及价值，实际图件字段到制图阶段补齐。
- `real_photo_slots`：required时至少一项，每项`name`、`location`、`basis`；schematic/有依据omit时填[]，schematic须列出针对性的替代图名（可同时计入额外1—3张）。与visual_policy一起传播至format_rules，不能审核时临时清空；重新判断有实质依据时同步更新两处及受影响图件/证据，无需重置旧正文和阶段状态。

`plan`必须形成内容需求、主响应模块和容量判断；有页数脚本再填严格预算、阶段模块前缀及预计范围，长文先通过Word代表性样章。字段和完整调用顺序见[内容模块与长文规划](05_内容模块与长文规划.md)。章范围包含图表，图表汇总不再加页；模块内部保存不限次数，用户交付最多三批。

## 原资料覆盖与充分响应

启动/规划时读本节前三项，模块写作读第四项，定稿读第五项。提取方法按01第八节执行；全部记录由AI建立，不要求用户填表。新状态schema=3.2；旧状态保留历史，先据实补齐本节再继续新编/实际变更模块，不重新init。

1. **实际文件与读取范围。** `startup.source_scope={roots:["原资料实际目录"],excluded:[{path,sha256,reason}],reviewed:true,conclusion:"附件总索引、来源目录和提供记录的实际核对"}`。roots可为目录或单个文件；所有实际文件必须在sources或有效排除项中，输出、状态、评分清单及读取缓存存别处。sources原有path/sha256/role之外增加稳定id（扫描器可生成）；清单role可为boq或bill。扫描不能读取的格式，登记`readable_copy={path,sha256,original_sha256,correspondence_reviewed:true,conclusion}`，实际核对原件与转换件的页/图/表及范围，不允许任意摘要充当转换件。PDF/Word/UTF-8文本和CSV、XLSX/XLSM/XLS有原生枚举器；旧XLS仅能提取缓存值，须回原表核公式与图形；缺库、加密或坏文件均报错，不算已读。

```bash
python scripts/source_coverage.py --state 项目/篇幅规划状态.json --scoring-checklist 项目/项目评分清单.json --text-output 项目/原文读取缓存.txt
```

2. **单元处置与需求。** 扫描生成`startup.source_coverage={version:1,inventory:[…],dispositions:[],extraction_review:{}}`，不自动通过阅读。inventory包含每份原件及转换件哈希、实际单元id/locator/text_sha256/flags；不要手改范围，来源变化重新scan。AI按原文填dispositions，每组`unit_ids`（直接使用inventory中的ID）、`status=reviewed`、`disposition=requirements|no_technical_response`、`conclusion`。前者填实际`requirement_ids`，后者填具体`reason`且不填需求；合并不能跨文件或混合不同处置逻辑。flags含visual/formula时须实际回看，填相应`visual_reviewed`/`formula_reviewed=true`及`manual_evidence=[{path,sha256,locator}]`。每个单元须恰好处置一次。extraction_review含`source_pass`、`scoring_pass`、`scope_reconciliation`三个`{reviewed:true,conclusion}`，记录原文遍历、评分反查及施工对象/工序接口核对的实际发现与处理。每项requirements在原字段之外填`source_refs=[{source_id,unit_id,quote}]`、`response_requirements=["该项需要落实的具体条件",…]`；引文须来自对应原文单元。扫描图中的文字等不能文本提取时，实际核验转录后才可加`manual_transcription_verified:true`，并保留该单元原图复核证据。

3. **评分原文与支撑关系。** `plan.scoring_basis={path,basis_sha256}`由上述命令从既有项目评分清单生成，仅冻结tender_source及items中的id/name/source_ref/criteria/max_score/excellent_range/excellent_note；completion、措施和模拟得分变化不使原文依据失效。每个criteria用从0开始的`criterion_index`定位。scoring=true需求各填唯一`score_refs=[{item_id,criterion_index}]`，scope保留该子条件原文，source_refs保留招标/有效补遗原文引文；评分清单全部子条件须完整、唯一分配。清单等实施需求scoring=false，可通过score_refs关联其呼应的一个或多个子条件；不强行把实施需求改写为评分原话。目录名和章节标题不能替代这些对应关系。

4. **模块充分性。** 在原模块复核JSON加入`response_review={checks:[{requirement_id,status:"adequate",conclusion,aspects:[{expectation:"与response_requirements某条完全一致",location,quote,adequacy:"adequate",conclusion}]}]}`。覆盖当前模块primary_for的全部需求及各项完成条件，每条quote为当前真实施工措施原文且至少20个非空白字符；句长只是防止空定位，不代表技术深度。泛泛表述、部分回应、错误方法或不具可行性的措施不得标adequate。scoring_review沿用优秀条件复核；两者复用原文，但不以评分条件替代普通实施义务。通过记录供40%/75%及成稿复用，实际变化只复查受影响责任。

5. **最终原件反查。** 在现有`内容溯源核验.json`加入`source_response_review={version:1,state:{path,basis_sha256},original_recheck:[…],scoring_recheck:{reviewed:true,conclusion},body_to_source_recheck:{reviewed:true,conclusion},unresolved:[],conclusion,module_reviews:[],responses:[]}`。state.path为实际项目状态，basis_sha256绑定来源、规划及模块的内容指纹，不绑定会随审计更新的gate/时间戳。以下只读命令输出该指纹和每份inventory的指纹/单元数，不修改状态，也不代替专业审核：

```bash
python scripts/source_coverage.py --state 项目/篇幅规划状态.json --check
```

original_recheck逐份原件填`source_id`、`inventory_sha256`、`reviewed_ranges=[[1,N]]`（按该文件inventory.units的一基序号，可拆成若干不重叠范围）、`status=reviewed`、`conclusion`，须重新从当前原件找漏项/不足，不能从已提取清单推导已审。N使用实际单元数；全部范围无遗漏。评分反查核优秀条件的当前正文证据，正文反查核事实/规范/计算/策划依据及图文一致。新发现事项先更新原requirements、模块和正文，未完成项不得强填[]。module_reviews填已登记、仍有效的模块复核`{path,sha256}`，自动复用其中response_review；继承模块或不能复用的需求在responses用同样checks行结构补当前稿审核。两处合计须逐项覆盖全部requirements、不得重复，全部引文在实际冻结DOCX中存在。content-review及delivery都会重核，评分报告同时核对同一评分依据指纹；全文交付还须与--state指向同一状态。范围外缺口不得借局部复审隐藏，按授权范围定点修订并如实报告。

## 项目脚本替换与唯一来源

包内只保留一个`*页数硬审*.py`，文件名可随项目变化；必须保留接口`EXPECTED_BODY_PAGES`、`PAGE_TOLERANCE`、`FRONT_MATTER_PAGES`三个字面量整数，最终审核支持`document --report 路径`及0/2/3退出码。上下限由目标±容差决定。不得把页数目标写成Skill、通用脚本、工作流或独立维护参数JSON中的固定规则；状态和报告仅保存读取所得快照及来源。

`编制流程门禁.py page-rule`输出自动识别的来源文件名与规则。`run-page-audit`自动调用该脚本；加`--pilot`时测量代表性样章文字量并导出Word PDF，加`--stage 40|75`时由通用测量器读取同一来源并调用Word，只测量阶段稿而不执行最终范围判定，无需项目页数脚本实现阶段模式。

GH的`input/project/`内保留当前项目唯一页数脚本，通用脚本位于`audit/common/`。换项目时替换页数脚本并使用新状态路径。GH命令在子命令前加`--page-dir input/project`，本机默认在技能scripts目录自动发现。当前项目的规则据实调整时，保存旧状态及证据，按`page-rule`更新当前状态的`page_rule`快照并校准预算。重新preflight，重测受影响的样章、阶段稿及最终稿，保留旧报告供追溯。

各项目的章节、字体字号、照片主题、规范和控制值由AI按当次资料及编制前提示生成运行期规则。字号在篇幅规划前确定，编排与审核使用同一规则。

## Word实测通道

本机Windows能执行COM时直接运行。依赖为Python 3.10+、Microsoft Word和pywin32。

```bash
python scripts/编制流程门禁.py run-page-audit --document 项目/stage-40.docx --stage 40 --report 项目/stage-40-word-pages.json
python scripts/评分响应核验.py 项目/项目评分清单.json --phase 40 --document 项目/stage-40.docx --report 项目/评分40.json
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json checkpoint --stage 40 --document 项目/stage-40.docx --report 项目/stage-40-word-pages.json --score-report 项目/评分40.json
```

先校准40%，再校准75%，替换相应阶段数字及文件名。阶段Word报告为MEASURED，由checkpoint结合阶段评分、内容及剩余预算判定。PROVISIONAL允许继续编制，Word恢复后补测原阶段快照，最终验收须取得两个阶段的Word实测PASS。

网页版如已有远程链路：上传阶段DOCX至已配置仓库的`input/project/stage-40.docx`或`stage-75.docx`，触发`Word stage page measurement`并读取报告；代表性样章上传`input/project/pilot.docx`，触发`Word representative sample measurement`，取得Word页数/文字量报告和实际导出PDF，再由AI逐页复核并运行本地pilot门禁。**现有GH工作流不随本技能包自动升级**；远程必须运行本次脚本版本，生成相同schema和SHA256。正式审查同样提交本次format_rules及脚本；仅安装Skill不能改变Runner仓库代码。未升级时报告不满足新门禁就报告阻塞，不降级伪报。

暂时无法调用Word时，保存阶段快照，按上面的评分命令为同一DOCX生成评分报告，再用实际LibreOffice估值登记。估值阶段须在最终验收前补Word实测。

```bash
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json checkpoint --stage 40 --document 项目/stage-40.docx --actual-pages 20 --engine libreoffice_estimate --allow-estimate --score-report 项目/评分40.json
```

仅数字测量示例，不能拿20页作为真实项目数据。

## 静态核验与规则

```bash
python "scripts/Word正式交付硬审（不含页数）.py" 项目/final.docx --rules 项目/format_rules.json --static-only --report 项目/静态报告.json
```

format_rules由AI按有效招标、补遗及编制前提示自动生成。无明确要求时封面与一级目录共第1页，正文第2页开始。至少包含`required_level1_titles`、`font_rules`（字体字号详见下节）、`required_figures`、`required_real_photo_slots`、`photo_delivery_stage`及与startup一致的`visual_policy`。招标指定名按07登记并优先采用。无指定时三图分别命名施工功能分区示意图、施工进度横道图、施工进度网络图，每项`hard=true`、keywords含图名，默认`color_required=true`；增补/替代图及配色例外按下方“图件、照片与例外字段”。

### 格式与目录

先按部位提取招标及补遗的字体字号、适用范围和原文位置。编制前提示词明确指定的字号直接采用，仅未指定的部位参照招标。字型在有效招标硬性要求内采用提示词指定字体，未指定时参照招标。把决定和来源写入同一 `format_rules.json`，可在 `font_rule_sources` 保存提示词原文及招标位置。

`font_rules` 按 `body`、`heading1`—`heading3` 配置 `name_east_asia`、`name`、`size_pt` 或 `bold`，按项目实际填写字段。把提示词明确的字号按部位填入 `prompt_font_sizes`，审核读取时覆盖该部位的 `size_pt`，其余读取 `font_rules`。三号、四号、小四可写为字号名或16、14、12磅。仅指定正文普通段落时填 `font_body_scope: "text"`。另有表格或题注要求时使用 `table`、`caption`。历史规则缺该字段且未指定正文提示词字号时，仍按原有正文范围解释。确认无字体字号规则时用 `{}`，有任何有效要求即填入对应字段。

在编排样章或正文前运行 `python "scripts/Word正式交付硬审（不含页数）.py" --rules 项目/format_rules.json --print-font-rules`，将输出的生效字体字号应用到对应Word样式。静态核查校验格式参数，Word格式审核对照实际字号和字体；实测阶段使用该排版。格式决定变化后重新排版并更新受影响的测量及审核。

前置页设置使用现有format_rules内的`front_matter`，不新增配置文件：`cover_required`（布尔）、`toc_levels`（例如[1]或[1,2,3]）、`cover_page_range`和`toc_page_range`（文档实际前置页范围）、可选`cover_keywords`（有效招标要求的封面字段）、`source_ref`（格式原文/有效补遗位置或默认依据）。目录及封面范围可重叠；无封面/目录须有有效依据，分别设false/[]。页数脚本独占`FRONT_MATTER_PAGES`；规则的`body_start_page`若填写必须等于该值+1，不另设目标或扣除数。无页数脚本时仅按格式依据定位正文（默认第2页），不执行页数目标校核。单独封面、跨页多级目录等按当次要求生成范围，不硬套首页。封面不得借正文或“目录”两字冒充有效信息。

默认标题为章/节/一、二；招标另定时AI在`heading_patterns`生成`1/2/3`三个正则，各自第一捕获组须是可解析的中文或阿拉伯整数编号（例如一级`^([0-9]+)\\s+.+$`）。始终用真实Word 1/2/3级大纲，逐级比对目录和导航。静态及Word硬审按父子关系核对每章有节、每节有三级标题，列出缺失的章和节；现有样式、编号连续性及非机械化检查同时执行。AI在拟纲及定稿时逐节复核评价维度、节名与正文承接。定稿复核登记在原有内容核验记录，交付时检查覆盖和引文归属。仅允许必要的前置页/正文边界分页；正文内部沿用连续排版规则，检查空白页及图前留白。静态审查不能确认真实页位，须Word实测。

自拟二级标题中的逗号、分号串句由静态脚本拦截，语义和简练度由AI复核。招标或有效补遗逐字锁定的节名，在现有格式规则的可选 `locked_level2_titles` 逐项登记 `chapter`、`section`（均为实际正文含编号标题）与 `source_ref`（招标原文位置）。例外仅匹配指定章与节，不得为自拟标题补录例外。

正文标题对齐为硬性要求。一级章标题和二级节标题设为居中，三级标题设为左对齐，优先配置在对应Word段落样式。静态检查核对段落直接设置和样式继承，Word实排复核实际对齐。任一级不符即FAIL，报告列出标题、位置、期望与实测。招标或有效补遗明确另定时，在同一规则文件的`heading_alignment`按`"1"`、`"2"`、`"3"`填写相应级别，取值为`left`、`center`、`right`或`both`，并在`source_ref`引用原文及位置。该规则适用于正文标题，前置自动目录按下列制表位与缩进规则排版。

目录默认采用Word原生自动目录及TOC 1—3等对应样式，显示页码、页码右对齐、点引导符；自定义目录也须“标题＋真实制表符＋页码”，配置真正的右对齐制表位及点引导符，不能手打空格/句点。所有层级页码末位对齐同一版心右边界，左缩进体现层级；长标题自然换行并合理设置续行缩进，保留页码空间，避免页码孤行、挤压及越界，不缩到难读、不改正文格式、不强制分页。

沿用`front_matter`，可选`toc_layout`默认`{show_page_numbers:true,right_align:true,leader:"dots",right_inset_pt:0}`，位置按当前版心自动计算，不硬编码A4制表位。招标/有效补遗明确另定时AI填相应开关、leader（dots/none/dashes/lines）或版心内右缩进磅值，并必填`source_ref`引用有效格式依据；`show_page_numbers:false`表示必须隐藏目录页码，不是跳过检查；`right_align:false`时存在多个候选制表位须复核实际使用位置，不能因未使用的制表位误判。目录页码可识别阿拉伯/罗马编号，正文标题末尾数字保留；对称页边距、原生目录嵌套域受缩进影响的光标坐标等无法可靠测量情况转WARN并逐项核对实际渲染。不要求用户改通用脚本。目录层级、封面结构及页数来源仍用前述字段和唯一页数脚本。

静态检查逐目录项核对真实制表符、段落/样式继承后的制表位与引导符；手打点线即使外观齐整也不能冒充合格。原生TOC首项须将范围限定在可见域结果及相邻段落边界内，防止Word自动扩展到整个目录域。Word定位页码及标题末字时显式传递反向、范围停止和无格式查找参数，避免长标题重复文字误定位。Word审查复核有效制表位、实际页码右边界、标题末行与页码同列/同行及当前正文显示页码；明确错误FAIL，复杂分栏/不可可靠定位等WARN，须按现有WARN记录逐项处理。脚本只检查、不修改DOCX；不能把静态配置PASS当作实际视觉合格。

最终在交付副本中更新目录字段及页码（需要时重复更新至稳定），保存后重新分页；核对目录名称/层级/顺序/页码与正文及导航，目视复核长标题、一至三位页码和跨页衔接，在既有内容核验`visual_review.conclusion`记录目录效果。更新导致前置页数量变化时，由AI按实际页位修正唯一项目页数脚本并复测受影响证据；冻结后再跑正式检查，避免审核器只读更新域却未保存到真正交付文件。

### 数据表排版

招标及有效补遗明确要求优先；默认表格在版心内整体居中，表头及名称/数量/时间等短内容水平、垂直居中，长说明左对齐且通常垂直居中。清除单元格意外继承的正文首行、悬挂、左右及字符缩进；保留确需的编号列表层级。列宽按实际内容、字号及版心分配，适当留内边距，长文自然换行；避免短名称碎行、数字单位分离、文本裁切和表格越界，不机械均分列，不通过空格/制表符/手动回车凑齐、不擅自缩字号或改变正文格式。跨页表按需要重复表头，合理处理行的跨页，不强制新开页。

AI在同一`format_rules.json`自动填写`table_layout.tables`，按正文主文档中非嵌套表格的顺序索引（含照片/布局表）：例如`{"tables":[{"index":1,"kind":"data","header_rows":1,"column_roles":["short","short","short","long"]}]}`。`column_roles`须逐列按实际内容判断，不能把整表机械归为短文；同列混合内容或复杂表由AI按渲染复核。照片框、图形表、封面布局等可写`kind=photo|figure|layout`并提供实际`reason`，不得以此排除普通数据表。默认配置为`table_alignment=center`、`header_alignment=center`、`short_text_alignment=center`、`long_text_alignment=left`、`vertical_alignment=center`、`zero_indents=true`；有效招标格式另定时AI填对应值及`source_ref`，不要求用户改通用脚本。

现有静态/Word硬审核对有效样式继承后的缩进、表格/单元格对齐及可可靠识别的版心边界，明确错误FAIL；未确认列角色、嵌套/合并、条件样式或不能可靠测量的情况WARN，不能凭脚本属性PASS认定视觉合格。AI查看Word实际导出页面，逐表核对短名、数字单位、长文换行、列宽及跨页衔接，在既有`visual_review.conclusion`和`WARN处理.json`留定位及处置证据。表格排版改变后重分页并复测受影响的页数/格式检查，保留既有有效项目状态及未变审核记录。

### 语言检查

语言检查覆盖正文、表格、页眉页脚、文本框及脚注尾注的可见文本；明确内部用语FAIL，疑点/引用施工审核语境WARN。AI逐条语义复核，定点修正；有效施工表述保留并在既有`WARN处理.json`留具体证据。脚本不会自动删词或修改正文，逐段语义审查仍不可省略。

### 图件、照片与例外字段

全篇内容图与内容表各自用连续阿拉伯数字题注。静态核验及Word硬审复用题注检查，核对图表与相邻题注是否逐一匹配，并拦截缺号、跳号、重号或次序颠倒。照片框计入图号，确属纯布局的表框不计表号。数据表沿用现有`table_layout`索引规则。

三图及增补/替代图以独立PNG嵌入DOCX，使用`图1 图名`等独立图题。图片与图题同段或直接邻段（仅允许空段间隔，不能隔其他标题/说明段）。默认彩图检测会读取实际嵌入图片字节，彩色像素≥1%、前景中彩色像素≥4%、至少两种有实际面积的色系；这是筛黑灰图及小角标的初始技术阈值，不能代替查看颜色是否真正作用于主体。图件宽≤高。复杂Word绘图先导出清晰PNG，避免无法检测的对象被假报通过。

`visual_policy`完整沿用启动记录，不新增配置文件：
- `real_photos.decision=required`时照片清单非空；schematic时为空，`replacement_figures`至少一张针对主题的实际示意图，不能用必备三图充数；omit必须有明确特殊要求override。`reason`写项目整体价值判断。占位只能存在于选择照片的draft稿。
- `additional_figures.names`默认1—3个三图之外的功能图名，`reason`写为何这些图有助施工理解或评分响应；特殊数量使用本项override，不因篇幅紧张自行省略。替代实景图可与增补图重合，清单只登记一张，图表空间不重复计数。
- 三图、全部增补图及替代图登记到同一`required_figures`：`name`、`keywords`、`hard=true`、与有效配色一致的`color_required`。非三图还须`purpose`（功能价值）、`location`（正文位置）、`context_anchor`（图旁实际说明原文，至少20个非空白字符，位于图题前后4个正文块内）。机器检查图片真正嵌入、图件独立及相邻说明存在；AI核对其逻辑、针对性和技术依据。
- `color_figures.mode=color`沿用默认多色阈值；monochrome须override并配置相关图`color_required=false`，实际嵌入图彩色像素占比不得超过0.1%；custom须override、布尔`color_required`及`metrics`明确`min_color_ratio`、`min_foreground_color_ratio`、`min_hue_groups`、`max_color_ratio`，按有效单色/其他配色要求设阈值后实际目视复核。不能用custom无依据放宽默认要求。
- 每个override含`source_type=prompt|agents|tender`、`source_ref`（消息/文件及段落位置）、`quote`（相应原文）。临时提示词及AGENTS.md的明确规定优先于通用默认，招标硬要求优先；无法消解冲突仍按既有流程处理。无特殊要求不填写override，不能伪造依据。

同一轮相关图件/占位修改结束后统一Word重排并跑通用/独立页数双硬审，不逐张小改重复调用；既有样章和40%/75%时点照常执行，最终冻结文件完整验收，变更后只复测受影响证据，但全部最终报告须绑定当前文件哈希。无照片方案不产生照片真实性警告；有照片仍按原始素材核验。`visual_policy.py`和`project_response.py`是流程与格式硬审的共用依赖，远程调用时须与它们放在同一目录。

照片占位主题必须与清单name一致：一格表格，可见边框、行高≥50pt，含`【实景图占位：主题】`及`需插入现场照片`；用单独图题连续编号。draft可占位。真实照片条目填`replaced=true`、`source_record`、`source_verified=true`、`image_sha256`（实际嵌入图片的哈希），图题含主题名且图片邻接。final不得残留占位文字。

## 内容溯源记录

`内容溯源核验.json`须绑定当前DOCX的`document_sha256`；它是AI专业审查留下的证据，不能由脚本自动填PASS。

使用`编制流程门禁.py --state 状态路径 template --kind module|content|parameter|conflict --output 新记录路径`生成空结构；module另传`--id/--source`，content另传`--document`。模板不覆盖原文件，默认pending/false；AI填真实证据，模块提交和content-review即时核验。pending/partial保留未完成事实，但不能通过最终验收；不得批量改为verified/handled替代核查。参数或冲突模板对象填妥后并入原记录的对应数组，不另建台账。

- `source_checks`：十项名称必须逐字使用：评分标准；硬性响应与否决格式；知识库冲突；数字条款原话；点名重难点；缺失待核实；企业资料；规范控制参数；初稿原文溯源；定稿最新文件与系统要求。
- 每项`item`、`status=verified|not_applicable`、`conclusion`；verified必须`evidence`数组，每项`path`、`sha256`、`locator`（页码/图号/条款/MD段落）。not_applicable须`reason`；评分、硬性要求、初稿溯源、定稿核验不能标不适用。
- `latest_confirmation`填`confirmed_at`、`reply_source`、`conclusion`。可引用会话已明确答复与最新文件检索记录；无更新证据时应询问。不能把缺文件推成无更新。
- `parameters`：用于正文的关键控制值逐项登记`name`、`scope`、`kind=project_fact|standard_value|calculated|proposed`、`cross_source_search`、`occurrences`（所有相关候选值数组，每项value、unit、scope、path、sha256、locator；清单来源另标role=bill）、`status=consistent|resolved|handled`、`decision`、`body_locations`（数组；每项location、quote、value、unit、scope，quote须真实存在且值/部位匹配候选）。calculated补`calculation`（公式、输入、单位及作业条件），proposed补`feasibility_basis`；计算/策划的候选依据可用真实计算或策划记录，不冒充清单原文。有不同值须resolved并补resolution_evidence，或按清单记handled；后者须handling=bill_primary、source_status、recheck，正文取值须匹配role=bill的有效候选。避免写争议数值的项目不放“用于正文的参数”，保留到conflicts。若确无关键参数，填[]和有依据的no_parameters_reason。
- `conflicts`：保留全部已发现冲突。旧resolved字段沿用；按用户口径处理而原始资料未统一时，用status=handled、handling=bill_primary|avoid_detail、source_status（真实资料状态）、decision、evidence（真实path/sha256/locator数组，清单另标role=bill）、body_locations（实际location/quote）、recheck（关联章节、表格、图件的复验结论）。bill_primary须有清单证据；handled只表示编制处置完成，不宣称官方已确认。证据或正文处理不全仍阻断；不得删记录冒充无冲突。
- `construction_language_review`：`all_paragraphs_reviewed=true`及conclusion，只有实际逐段检查才可填。
- `visual_review`：沿用`three_color_figures_reviewed=true`、`caption_photo_reviewed=true`、conclusion；两布尔表示已经按当前有效配色及照片决策完成核对，不要求无照片方案虚构照片。conclusion须覆盖三图、额外功能图/替代示意图的实际视觉和上下文衔接、适用照片/占位及目录表格；配色例外说明依据与实际效果。

### 正文引用依据

在重要工法、关键参数、设计清单锁定做法、安全质量措施、验收判据、工期和主要承诺的对应正文段落写依据全名，按来源补规范编号及适用条款、文件条款、图号或清单编码。有计算或拟采用措施时说明事实、输入及判断依据。引用前查原件、版本和适用范围。

在既有内容核验记录的 `body_citations` 登记 `reviewed`、实际 `conclusion` 和 `items`。逐条填写 `subject`（所支持的具体事项，重复事项使用同一名称）、`source_name`（正文显示全名）、`locator`（正文显示的可回查位置）、`body_quote`（含措施和引用的同段原文）、`source_ref`（已核原文件位置、来源单元或权威网址）。用同一记录复核关键事项逐项标明依据，定稿核对已登记引文实际存在。局部复审填写本次改动的关键事项。

计数按实际正文中的事项、来源和位置去重。集中编制依据或引用文件清单、标题及封面目录不计。全文目标以15条为基础，长文按每4页一条向上取整并取较高值，按章节及关键事项安排。最终用本稿Word实测正文页数计算。数量不足为WARN，优先补有依据的引用。确受项目限制时在同一 `WARN处理.json` 登记 `report=content`、`check=正文依据引用数量`、实际条数、差额、已补事项及剩余原因。数量满足后仍复核重要内容的依据覆盖。局部复审按授权范围检查引用。

### 五项专业复核与两项参考的轻量记录

新编/实际变更模块的原复核JSON、当前最终`内容溯源核验.json`各加入同一`technical_review`对象：`version=1`；`checks`含applicability、constraints、number_basis、quantity_capacity_schedule_resources、issue_recheck五个键，每项为`{status:"reviewed|not_applicable",conclusion:"实际结论或不适用原因"}`。证据沿用正文探针、参数台账、评分及冲突记录，结论写现有定位/问题编号，不复制全套材料。模块记录只检查当前责任，定稿记录汇总全篇。

## 自然排版与末页留白

- **全篇静态检查与 Word 分页检查。** 正文不得通过手工分页符、段前分页、新页分节换页。静态硬审核查普通正文的直接设置和段落样式继承。「段中不分页」及以「与下段同页」把普通正文连接至下一段均判FAIL。标题正常带首段、图表及题注必要绑定可保留。正文与图表相邻的短引介可直接绑定对应图表或题注。Word 同时核查实际分页设置及前置边界。
- **末页与前页实测。** 取全篇物理末页及其前最多4个正文页，按「有效正文内容的最低底边至正文版心底边的距离 ÷ 正文版心高度」计算页底连续留白。排除页眉、页脚、固定页边距和空段占位。末页须严格低于20%，达到20%或测量不可靠判FAIL。前页达到20%触发WARN并输出该页和相邻页，不能只因比例判定人为换页。缺失应测前页的几何判FAIL。
- **异常处理。** 逐页对照 Word 实排，注明物理页、正文页、造成留白的对象及原因，按既有 `WARN处理.json` 留证。确认人为移段、空段或格式放大时须修复并复测。确因必要图表或标题与首段的自然分页，说明前页剩余空间和对象无法自然容纳的依据。禁止为填末页而扩大前面留白。篇幅不足时回查全篇预算，在对应章节补足有依据的施工方法、交接条件或验收证据。禁止重复内容、增加装饰图或放宽既定版式。局部修订按授权范围执行，需改动超出范围时如实报告冲突。

## 交付汇总

`WARN处理.json`含当前`document_sha256`、`items`数组；每项report=`word|static|score|page|content`、check（审核check.name）、status=`reviewed|not_applicable`、evidence、conclusion。即使没有警告也留空items，明确当前版本已复核。真实照片来源WARN用原始素材/登记核验；留白WARN引用Word导出异常页及相邻页证据。缺几何证据的SKIP不能直接写通过。

图表不足15个时，两份报告的`正文图表数量` WARN分别登记为`report=static`与`report=word`，可引用同一份实际计数及处置依据。

```bash
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json delivery --document 项目/final.docx --static-report 项目/静态报告.json --word-report 项目/Word格式报告.json --page-report 项目/Word页数报告.json --score-report 项目/评分最终.json --review 项目/内容溯源核验.json --warning-review 项目/WARN处理.json
```

局部复审添加`--mode local-review`，不要求旧状态。缺页数脚本不传page-report。新文件修改后旧SHA256审核失效。交付必须具备本版静态及 Word 报告、末页留白合格记录、前页完整实测和需要的逐页WARN处置证据。独立页数报告与实测须对应同一文件及实际总页数。draft仅DRAFT_DELIVERY_ALLOWED，final才FINAL_DELIVERY_ALLOWED。

delivery更新状态同目录的`流程交付结果.json`，供next判断。使用`--result`时另存同一份结果。旧版结论用于追溯，采用新版规则放行时对当前稿补正文引用复核、重跑静态和Word格式检查，再执行delivery。

task_complete和formal_release仅在全文final全部通过时为true。草稿通过为DRAFT_READY，局部通过为LOCAL_REVIEW_ALLOWED并记录local_review_complete=true。失败退出2，异常退出3。外层原样传播退出码并检查本次结果。局部复审在内容核验记录填`local_review_scope={user_quote,reply_source,scope,base_document:{path,sha256}}`，保留真实授权和原稿。其余可修复事项继续处理。

## 依赖与失败恢复

静态检查需Pillow，DOCX生成可使用环境已有文档能力；WindowsWord审查需pywin32；异常页PNG导出优先复用PyMuPDF，缺失时保留Word PDF/EMF。开工一次检查依赖，优先已安装环境，不反复下载。断线前保存阶段快照、正文源、状态和报告；恢复时核对哈希与真实进度。缺Word最终能力只能报告未完成Word验收，脚本语法/静态测试通过不能证明全链路通过。

原资料扫描按文件类型使用pypdf、openpyxl、xlrd；仅预检/安装当次实际需要的依赖。宏和公式不执行，旧XLS公式、图形及PDF图像须实际回看。读取失败返回3，已扫描但未完成阅读/处置时检查返回2，均不得当完成记录。
