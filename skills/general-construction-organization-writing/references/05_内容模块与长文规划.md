# 内容模块与长文规划

## 内容与预算的建立顺序

1. 读取当前项目资料、评分及唯一页数脚本；集中解决启动问题。
2. 拆分评分子条件、实施范围、必备工序、强制响应为`requirements`，保留原文位置与文件哈希。
3. 按招标目录和施工逻辑形成章—节—内容模块。每项需求恰好一个主响应模块，其他模块只承担协同接口，避免跨章复制。
4. 逐模块列出施工对象、工序与技术深度、资源/检查/偏差处置、图表及接口；判断真实内容是否支撑篇幅。资料缺口先质询；只有标题、通用制度或机械增表不能算容量。
5. 预算拆成文字、表格、图片三个互不重复的等效版面量，可用小数。机动量全篇只计一次。40%和75%实排后用前缀实际占页重估剩余预算，优先调整有评分责任或施工交接、放行、验收仍需深化的模块。末页留白是连续排版的结果，禁止锁定普通段落、推标题换页或调版式凑篇幅。
6. 运行preflight；长文只获样章权限。真实Word试排后重算预算，再取得批量正文权限。

这些规划和核查由AI根据项目资料完成，不让用户手工填JSON。脚本检验结构与版本；内容是否真实、技术深度是否充分，须逐项专业审查。

## plan字段

| 字段 | 要求 |
| --- | --- |
| `revision` | 正整数，实质调整递增；修改任何规划字段后重新准入 |
| `requirements` | 对象数组，每项`id`、`scope`、`evidence`及`scoring`（布尔：是否承担招标评分子条件，schema 3.1必填；为true时scope保留该条件原文）；证据含实际`path`、`sha256`、`locator` |
| `modules` | 按最终正文顺序排列，字段见下表 |
| `capacity_review` | `all_requirements_mapped`、`scope_supports_volume`、`no_padding_or_repetition`仅实际审查后填true；`conclusion`记录依据，`unresolved_gaps`须空数组 |
| `chapter_plan` | 每章`chapter`、`basis`、`page_range`；覆盖所属模块预算，按评分/复杂度分配 |
| `planned_total_body_pages` | 规划阶段为全部模块预算＋机动量；已有有效Word前缀时为实测前缀＋剩余预算＋机动量，必须在页数脚本目标±容差内 |
| `figure_table_pages_estimate` | 全部模块表格＋图片的统计子集，不重复累计 |
| `reserve_pages`、`planning_notes` | 非负机动量及真实收敛逻辑 |
| `checkpoint_module_ids` | `40`、`75`对应有序模块ID数组，必须是连续正文前缀；75晚于40且仍有后续模块 |
| `checkpoint_completion_basis` | 两节点按施工内容和评分责任判断完成度的依据，不能机械按页数比例 |
| `checkpoint_expected_page_ranges` | 各前缀模块预算派生区间；最大偏移为前缀预算5%向上取整且至少1页，不任意放宽。该前缀已有有效Word实测时可据该实测修订 |
| `pilot_plan` | 长文填`module_ids`（至少两个代表模块）、`coverage=["narrative","table","figure"]`及`basis`说明抽样代表性 |

`modules`每项：

| 字段 | 内容 |
| --- | --- |
| `id`、`chapter`、`section` | 稳定唯一ID及真实目录位置，章名与chapter_plan一致 |
| `scope`、`basis` | 实质范围/应达到的技术深度及分配依据，不只写章名 |
| `requirement_ids`、`primary_for` | 本模块覆盖需求及主响应需求；主响应须属于覆盖范围 |
| `evidence` | 内容依据，含实际path、sha256及locator；不是历史案例事实 |
| `estimated_normal_chars` | 非表格正文非空白字符估量，试排后按实测文字密度重算 |
| `text_pages`、`table_pages`、`figure_pages` | 分别为文字、表格、图片/实景框等效空间，不能重复计数 |
| `planned_pages` | 上述三项之和；大模块按实质工序/责任拆开 |

无页数脚本时仍建立requirements、modules、chapter_plan及capacity_review，跳过数字预算和Word页数节点。不要把项目目标写进通用Skill、GH工作流或第二套固定参数配置。

适用专业检查项及限制条件写入相关模块scope/basis，不增设一套规划。unresolved_gaps指仍妨碍编制且没有处置的缺口；按用户口径规避图纸争议/采用清单且有完整措施的事项保留在独立冲突记录，不能把原始未统一误当“无法继续”，也不能谎称原始冲突已获官方确认。

## 长文样章门禁

通用策略由`planning_policy(target)`派生：目标达到200页才强制早期样章；模块上限按目标约5%取整并限制在12—30页；代表性样章范围根据目标约2%—4%派生并限定到适合试排的小样规模。使用当前返回值，不把任何一个项目的页数或模块数量当模板。

用本项目正式字体、行距、页边距、正文前置页结构编排样章：取至少两个模块的真实代表段落，实际嵌入表格和按有效配色要求的图；按项目图文决策，选照片时包含照片/带框占位，选示意图时包含对应示意图，不要求无照片方案额外造照片框。正文/图表混排时估算等效面积，不能把整页分别计到多种组件。Word导出的样章PDF须逐页查看；表格按04规则核对整体与单元格对齐、零意外缩进、列宽、短名/数字单位换行和跨页衔接，同时记录图字可读性、适用照片框/替代示意图和留白处理。短项目无强制样章时，在模块排版和最终复核中完成同样的表格检查。

```bash
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json preflight
python scripts/编制流程门禁.py run-page-audit --pilot --document 项目/pilot.docx --report 项目/pilot-word-pages.json
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json pilot --document 项目/pilot.docx --report 项目/pilot-word-pages.json --analysis 项目/pilot-analysis.json
```

`run-page-audit --pilot`必须在可调用Microsoft Word的Windows通道运行；报告包括`measurement_role=pilot`、当前DOCX哈希、项目规则、正文页数和Word测得非表格正文字符量，并导出同名`.word.pdf`。封面与完整目录实际占页须按Word页面核对，并与项目脚本的前置扣除值一致；样章用正式目录结构/等效前置页，不因样章较短就省略前置页。最终目录更新后再次核对，变化时修正项目脚本并重测受影响证据。普通文字量与非表格文字面积对应；不能用Python猜测值或LibreOffice报告冒充Word。

`pilot-analysis.json`由AI实际看样章填写：

- `document_sha256`、`module_ids`绑定快照及计划代表模块；
- `format_rules={path,sha256}`冻结实际项目格式规则；
- `font_and_spacing_reviewed`、`table_layout_reviewed`、`figure_readability_reviewed`、`photo_frame_layout_reviewed`实际复核后填true（无照片方案核对未遗留照片框及替代示意图布局，在结论中说明）；
- `visual_evidence`记录实际Word导出PDF及必要页面截图的path/sha256，必须引用本次测量器导出的PDF；
- `normal_text_pages`、`table_pages`、`figure_pages`为正的等效版面面积，三者合计与Word样章正文页数相容。

pilot通过后，按`normal_chars_per_page`重新估量各模块的正文文字量/页数；差异要有内容与格式依据，不只是改数字凑总量。重新分配必要内容和图表，更新revision、总量、章区间及阶段预算。然后：

```bash
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json preflight
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json draft-ready
```

只有`PRE_DRAFT_ALLOWED`才批量编写。密度校准只改善预算，仍须专业审查内容；样章格式、PDF或来源改变使记录失效，重新实际试排。无Word能力时保存规划与样章，明确阻塞；不绕过长文试排去写完全文。

## 模块保存、恢复与合并

每模块立即保存MD/TXT/DOCX正文源，禁止用生成器代码、状态JSON或标题占位代替。保存复核记录，字段为：`module_id`、`source_sha256`、`covered_requirement_ids`、`fact_sources_reviewed`、`technical_depth_reviewed`、`interfaces_reviewed`、`repetition_reviewed`、`conclusion`、`probe_quotes`。四项复核只有完成后填true；正文探针至少两段不同原文，每段至少40个非空白字符。

同一复核记录新增（不另开审核文件/阶段）：
- `construction_language_review={reviewed:true,unresolved_count:0,conclusion:"实际语义复核结论"}`。检查审查意见、内部状态、待办和自评痕迹，发现问题先定点修正，不改掉正常施工技术含义。
- `scoring_review={conditions:[…],conclusion:"针对当前责任的结论"}`。逐项覆盖本模块`requirement_ids`中scoring=true的条件。每项含`requirement_id`、`criterion_quote`（等于需求scope的评分原文）、`response_quote`（当前模块实际施工措施原文，至少20个非空白字符）、`evidence`（招标/项目依据，path/sha256/locator）、四项实际判断`targeted`、`technical_depth`、`project_basis`、`substantive_response`及`status=satisfied|deferred`、`conclusion`。缺项或深度不足先补强当前模块，不用true冒充审核；deferred仅用于跨模块尚未完成的剩余条件，补`remaining_condition`、`responsible_module_id`，本模块应完成措施仍须充分。轻量复核不填self_score，不凭局部措施宣称整个评分项完成。无评分责任时conditions=[]并说明`not_applicable_reason`。
- `technical_review`：version=1及五项checks，按04的轻量格式复核06第一节的当前适用责任；不适用写理由，来源/正文引文复用上述证据与probe_quotes。只对新编/实际变更模块要求该字段，既有有效模块不补造历史。三项经验参考在规划时考虑、最终汇总，不要求每模块重复统计。
- 40%/75%全局校准复用未变模块结论，核对跨章关联、总体覆盖与篇幅，不重复完整审核。模块源、评分/项目依据变化只复核受影响部分。

已有3.0状态及模块记录保留有效，不因升级重新init、不重跑未变历史审核；新写/实际变更模块使用新字段，旧规划缺scoring时AI按原文识别本模块责任并在conditions中登记，不能默认无责任。新登记模块同时记录责任指纹，后续依据改变即提示定点复核。脚本只检查记录及证据绑定，不能替AI判断技术深度。

```bash
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json module-checkpoint --id M01 --source 项目/正文/M01.md --review 项目/复核/M01.json
```

登记正文源/复核哈希、实际文字量和恢复点；目标长文有文字密度时输出滚动估算，异常提示先复核内容/图表预算，必要时提前Word测量。估算警示不能当真实页数，阶段Word硬门禁仍执行。已被阶段快照使用的模块更新会使旧阶段记录STALE，禁止继续盲写，先更新实际快照与Word报告。允许返修已经保存的模块；不得丢弃旧正文重置状态以消除失败。

新模块按规划顺序保存；到40%/75%节点时，脚本阻断后续新模块登记，须先完成有效阶段校准。按计划到40%/75%时，将全部对应前缀模块实际正文合并为DOCX并测量；登记checkpoint，失败时保留实测，调整内容/剩余预算并重新preflight、draft-ready、复测。不能只修改最终预测值或扩大阶段窗口。评分核验同时检查已完成项。

```bash
python scripts/编制流程门禁.py --state 项目/篇幅规划状态.json final-ready --document 项目/final.docx
```

final-ready检查全部模块源及复核记录新鲜、探针存在，以及规范化正文分块至少90%进入合并DOCX；防止只保留探针和漏合并主体。该检查为辅助证据，不能证明语义等同或所有内容正确，最终仍逐章核对。修改表述较多导致覆盖失败时，先更新真实模块源与复核，再重测受影响阶段。最终通用Word硬审、独立页数硬审、内容溯源及delivery不可省略。

内部写作/保存模块不限数量；最多三批只约束对用户的交付，不限制模型分块、断线恢复和内部快照。
