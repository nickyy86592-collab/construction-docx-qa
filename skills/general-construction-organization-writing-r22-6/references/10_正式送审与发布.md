# 正式送审与发布

## 开编和阶段实排

同一个编制状态只绑定一张任务单。用当前技能包的脚本生成任务，版本、审稿程序指纹和批次由程序写入。项目编号、提交方式、页数和封面取有效招标及补遗。由有效原文确定预估篇幅与逐点章名。项目内只有一份生效的页数脚本，按招标调整已登记模板的常量。格式、评分、清单、资料溯源、计划、暗标等执行本包原审核。项目允许无页数目标时，整册仍执行 Word 版式审核。

工作目录只用于本批。项目状态、招标原件、读取凭证、模块、40%/75%阶段稿及评分稿都放在这个目录内。输入资料及证据引用按对应 JSON 的既有基准保存相对路径。原阶段通过记录保留，跨目录迁移后用真实原件和当前报告复核。编制版本号取技能包的 release-profile.json，不由文件名猜测。若生产配对表还没有对应项，记录具体配对缺项，保存可核的工作底稿。

从已登记的私有 GH 生产仓取得 release-trust.json。以本包路径调用：

```bash
python scripts/release_task.py --project 项目目录 start --project-id 招标项目编号 --submission whole --trust release-trust.json
python scripts/release_task.py --project 项目目录 prepare probe 编外路径/probe.zip
```

r22.6 使用 whole。项目显示名与页数参数填入项目页数脚本常量。任务生成后，项目责任、版本和批次锁定。原状态存在时按同批接续。将冻结 ZIP 上传至登记的私有收稿目录，取得该文件的 Drive ID。使用有运行权限的生产入口：

```bash
python scripts/release_task.py --project 项目目录 dispatch 编外路径/probe.zip DRIVE_FILE_ID
python scripts/release_task.py --project 项目目录 accept 回执下载路径/回执.zip --request-id 准备阶段输出的请求号
```

dispatch 使用一次配置的 CONSTRUCTION_GH_DISPATCH_TOKEN。默认在私有生产仓发起 Actions 任务。生产配置登记公开入口时，脚本从公开入口发起，由该入口将文件 ID 和摘要转交生产仓。也可直接调用对应工作流的 workflow_dispatch，提供冻结包文件 ID 和 SHA-256。GitHub 接受启动后跟踪生产运行号。在私有回执目录取同请求号的回执 ZIP，accept 验证签名和本地原字节。通道试稿由脚本生成，Windows Word 应实际打开样稿、读到本批标记并计页。只写“运行器已启动”无法通过本批通道门禁。通道问题按现有授权的私有路径查到具体环节，先保留实际可核的底稿并继续能做的工作。

收到试排回执后按04执行 preflight。pilot、stage-40 和 stage-75 都可用同一个 prepare、dispatch、accept 签发真实报告。阶段文件分别命名为 pilot.docx、stage-40.docx、stage-75.docx。回执中的 pages.json 是对应项目规则的实排结果，阶段 figure-pages.json 可供同稿技术核验。逐点任务的合册阶段报告用于核定完成范围、版面和剩余预算。提交件的单点和总页数按实际分件执行最终硬审。逐一完成原有模组、阶段评分和核验记录，checkpoint 采用校验后的报告。文件或规则改变，受影响阶段重新实排和复核。

## 定稿与审稿程序匹配

定稿 Word 名为 design.docx，运行期格式规则为 format_rules.json。安装注册程序会把编制版本、审核脚本指纹和允许的交付形式写入 GH 的唯一配对表。工作流先核私有仓、可信分支、版本配对、冻结摘要和本批通道证据，然后才调用 Word。本批任务一直使用锁定的审核实现。不同项目可以使用同一 Runner，作业各有独立目录。

跑 measure 获得 static.json、delivery.json 和适用的 pages.json。档案中的发动记录保存具体失败位置。安排第三方复核或美化时使用同批当前稿件、交付形式和招标规则。Word 排版或实际提交文件有变化时重新冻结与实排。PDF 交付使用同一审稿 Word 的实测导出件，报告和最终字节逐项核对。

## 正式发布和返修

填齐原版要求的 review.json、score.json、warnings.json 以及相关来源和阶段文件。若提交 PDF，原版 review.submission_pdf 引用 measure 实际导出的文件及摘要。逐点提交 PDF 还须逐份核验该报告导出的实际 PDF。按03为用户另外交付完整的《施工组织设计技术评分模拟自评报告》，与正式投标文件区分并按项目授权私有保存。准备 publish 冻结包并走同一私有任务入口。程序在本次作业内运行原 delivery 完整门禁，核实测量和阶段报告的签名、本项目批次及实际哈希。正式文件从私有暂存逐一校验，通过后整批移入正式目录，再签发 GD 正式链接。上传中途失败时按失败回执定位并重新 prepare publish，生成新请求号。发布程序复用同批已核暂存内容。同一送审编号对应同一份冻结包，同一正式批次的已发布文件保持可追溯。

以通过签名校验的发布回执为准。校验失败、超限、缺证据、版本对不上、文件改动或上传未完成时，当前批次保持未放行。next 只有在核对本批正式回执后才确认任务完成。后续修订依据实际文件重新核对。工作稿可保存到工作目录，并用工作稿状态呈现。
